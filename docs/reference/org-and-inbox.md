### A reaction is durable, and a state is not news

A follow-up or another message on a subject automatically records what the user already saw (`reactedAt` on the thread, `readAt` on its answered messages, and the existing `known` mark). These receipts stay with the answers when messages are split, merged or moved. Splitting out the follow-up acknowledges the source when it has neither unanswered work nor unread words. Only this automatic close may reopen on a new reply or a valid `needs` state; an explicit user close stays closed.

An `answered` state alone never makes a card visible. The shared `hasThreadNews` predicate requires new reply text or an unread answer after the user's reaction. Repeating the same summary preserves `replyAt`. Titles, task links, moves, merges, splits, reopening and turn-end bookkeeping are not new replies. Late answers remain unread, and an old summary cannot cover an answer that arrived after the user's reaction. The user's reaction releases a pin too, so the card disappears immediately. Agents still cannot take off the user's pin. Overdue unanswered work keeps its existing rule. Agents still cannot mark answers known or close them before a real reaction, and handing a question to the user still checks `user_kind`.

Regression coverage: `tests/core/org/thread-reaction-ratchet.test.ts`, `tests/core/org/thread-view.test.ts` and the follow-up, split, answered sequence in `tests/e2e/browser/org-threads.spec.ts`.

- **A thread goes with its work** (`src/core/org/thread-follow.ts`; 2026-11-08, the user, after his thread stayed with the VP that had passed the work to another: "should go to walnut vp", then: once the task is moved under the other VP, the first no longer needs to monitor it). ## The inbox

- **The inbox is for what needs the user** (2026-10-05, the user: notifications only when asked, "only the most important information").
