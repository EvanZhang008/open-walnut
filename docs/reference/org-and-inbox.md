### A reaction is durable, and a state is not news

A follow-up or another message on a subject automatically records what the user already saw (`reactedAt` on the thread, `readAt` on its answered messages, and the existing `known` mark). These receipts stay with the answers when messages are split, merged or moved. Splitting out the follow-up acknowledges the source when it has neither unanswered work nor unread words. Only this automatic close may reopen on a new reply or a valid `needs` state; an explicit user close stays closed.

An `answered` state alone never makes a card visible. The shared `hasThreadNews` predicate requires new reply text or an unread answer after the user's reaction. Repeating the same summary preserves `replyAt`. Titles, task links, moves, merges, splits, reopening and turn-end bookkeeping are not new replies. Late answers remain unread, and an old summary cannot cover an answer that arrived after the user's reaction. The user's reaction releases a pin too, so the card disappears immediately. Agents still cannot take off the user's pin. Overdue unanswered work keeps its existing rule. Agents still cannot mark answers known or close them before a real reaction, and handing a question to the user still checks `user_kind`.

Regression coverage: `tests/core/org/thread-reaction-ratchet.test.ts`, `tests/core/org/thread-view.test.ts` and the follow-up, split, answered sequence in `tests/e2e/browser/org-threads.spec.ts`.

### Where Threads are stored: JSON files, or a database behind the experiment threads_sqlite

- **By default each node's Threads are one JSON file**, `WALNUT_HOME/org/threads/<taskId>.json`, read and rewritten whole under a file lock (`src/core/org/threads-store.ts`). **With the experiment `threads_sqlite` on** (Settings, Experimental), they live in their own database, `WALNUT_HOME/org/threads.sqlite` (`src/core/org/threads-db.ts`): one row per thread, one row per message, so a change writes only the threads and messages it touched. It still reads the node's whole set first, every thread the model's functions work on: one update is not a single-row cost (on a 1.2 MB node of 200 threads and 700 messages, measured twice on a shared dev host: an update 2.9 to 6.6 ms against 6.9 to 11.5 ms for the JSON file, a read 1.5 ms against 2.2 to 3.8 ms). Whether a thread changed is judged by its JSON text against what was loaded, never by the object being the same, so a mutation that changes an object in place is still written. It is a file of its own, never `tasks.sqlite`, so its schema version can never stop an older build from starting. Every function of `threads-store.ts` keeps its signature and answers the same on either (`tests/core/org/threads-sqlite-parity.test.ts`), so no route, op or prompt changes. Each node's threads are also kept as their JSON text in memory (one text per thread, at most 32 MB, the nodes used last kept), made at a load and at each write (only the server writes Threads), so a read is one parse and never shares objects with another caller. A read leaves out a closed thread past its week; the sweep deletes it for good, as it does in the files.
- **The move in** (`src/core/org/threads-backend.ts`), the first time the experiment is on: `org/threads/` is copied whole to `org/threads-backup/<time>/` (a copy, nothing is moved), every file is imported in one transaction, and each node is read back and compared with its file (thread count, message count, then full equality). Only an exact match marks the import done and switches; any difference undoes the import, logs a warning naming the node and the difference, and leaves Threads in their files until the next start. A database written by a newer build (a higher `user_version`) is refused the same way.
- **The files stay current** (`src/core/org/threads-sync.ts`), so turning the experiment off, going back to an older release and git-sync all keep working: a node that changed is written back to its JSON file in the old format, at once when it was not written in the last minute and otherwise when the minute is up, and every waiting node is written when the experiment is turned off. At shutdown every waiting node is written, and from then on each write goes to its file before its call returns; the writes of the requests the HTTP close drains are awaited once more after it, with a budget of their own. A node stays marked dirty until its file holds it, so a crash writes it at the next start, even a start with the experiment off; a write that fails is tried again. A write that began just as the experiment went off goes to the file, never only to the database. The hash, mtime and size of what was written are kept; **a file that changed outside** (an older build, a git-sync pull, a hand edit, the JSON mode while the experiment was off) **is read back in before its node is used: the file wins.** When the file changed outside while the database still held changes not yet in it, nothing is dropped whole: the two are merged by thread (`threads-merge.ts`; the file is the base, a thread only the database holds comes back, of a thread both changed the copy changed last by `updatedAt` wins, and no message of either is lost), after the database's copy is saved to `org/threads-backup/conflicts/<node>-<time>.json` and a warning logged. At a start with the experiment off, the changes a crash left only in the database go to their files before the JSON mode's first read or write. A file that is gone, that no longer parses, or that is empty while the database holds threads for its node is written again from the database; one that names a thread twice keeps the first. A failed move, a backup copy cut short included, removes the backup it made, so a try at each start never piles them up; the move is tried again at the next start, and a database that fails to open keeps the JSON files until then. git-sync keeps syncing the JSON files; `*.sqlite` is ignored there.
- **Only the leader keeps Threads**: a replica reads none and never opens the database. Tests force the experiment with `WALNUT_THREADS_SQLITE=1` (a test process only), and `WALNUT_THREADS_EXPORT_MS=0` writes each change through to its file before the store call returns, so the existing suites run unchanged on either store.

### A thread goes with its work

- **A thread goes with its work** (`src/core/org/thread-follow.ts`; 2026-11-08, the user, after his thread stayed with the VP that had passed the work to another: "should go to walnut vp", then: once the task is moved under the other VP, the first no longer needs to monitor it). A lead's open thread whose listed tasks all do their work in ONE other open lead's team (`ownerNodeOf`: the nearest node in the parent chain, except a task whose parent lead does not answer for its project and another lead does) moves to that lead's Threads with everything on it (`movedFrom` there), and closes on the old one as `dropped` with `movedTo` (`movedAway`; no close kind of its own, so an older release reads it closed); a lead another VP took over hands all its open threads on. The rule runs on task and thread changes and every 10 minutes, so any path that moves a task is covered; Main's threads never move by it, nothing moves to Main or a closed lead by it, and a thread handed somewhere on purpose (`movedFrom.kind: 'hand'`) is never pulled back.
