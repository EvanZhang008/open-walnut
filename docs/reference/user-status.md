# The user status: Needs you, Working, Waiting, Done

One status the user reads, the same on every surface; how a change of it is pushed up the org; and how one decision asked by several tasks shows once.

_Moved from the root `AGENTS.md` on 2026-11-11; the root file keeps a one-line summary of each rule._

## One status the user reads, the same everywhere

- **One status the user reads, the same everywhere** (`src/core/user-status.ts`, 2026-10-25, the user: "I don't even know what needs me"; one team read "0 needs you", "1 needs you" and "11 handed back" on three surfaces, because every turn end set NEED_ACTION). The state IS the task's own phase (2026-10-26, the user: "this status need to be self updated by task, can also be updated by leader ... task has status, we already have good task system"; one surface had counted letters, Board choices and reports on their own and said 5 need you where the phases said 1): **Needs you** = NEED_ACTION (or a live prompt), except a NEED_ACTION that only says its turn ended: while that turn's report is still to come (`sessions/report-pending.ts`: for a native Claude Code session the status side question 5 s after the turn stays quiet, else the 4-minute quiet timer or the ask) it reads Waiting, and a report of done reads Waiting on its lead to check and close it (2026-11-01: a wait on the user is Needs you, never Waiting, except Main's, a lead's and a team the user stopped; `tests/core/wait-on-user-is-needs.test.ts`), a wait on its lead or another task reads Waiting on it whatever its words say of the user. **Only a real ask reaches Needs you** (2026-11-02, the user through Main: two finished triage runs, a finished task and a Q&A answer sat there on Walnut's own sentences): its own ask, a wait on the user, a letter, a choice, a prompt, a failure, or a person's NEED_ACTION on a task with no session, or one a person set themself on any task (a request with no `x-walnut-caller-sid` stamps `needs_marked_at`, which holds until the phase moves again: `src/core/sessions/person-needs.ts`, every phase route marks it, `tests/e2e/person-needs.test.ts`). A turn with nothing asked reads **To read** (stored state `read`, 2026-11-02, the user: under Waiting they "looks kike they are waiting for my input"; then "I dont wnat serpeate to read": every surface draws it under Needs you through `shownState`, while the stored state keeps it out of every re-check, push, wake and `user_kind` gate; an older client reads the phase, and Org counts keep `needsYou` without it and `toRead` beside it). Every Needs you row carries one line saying what to do with it, `user_status.category` derived from facts, never a model's guess (`needsCategoryOf`, `needsLineOf`): **Review** for an open review letter, **Can close** for a finished result (with a Close button on Home and the Org rail), **Take a look** for an answer, a hand-back or an error, else **Decide** with what there is to read (`toRead`: `result` for a done report with no lead or an ask with no kind of the user's own, `answer` for a turn that answered his message, `turn` for a hand-back with no report, with the words its last turn ended with once the reconcile tick has read them: `sessions/last-words.ts`, `Task.last_words`), while its NEED_ACTION phase keeps it on his list; a routine run's `result` (and a triage run's `turn`, whose asks are its letters) closes itself (`src/core/routines/run-close.ts`, from the status sync, so a turn end no `session:result` reported closes too; a triage run through its own bookkeeping). Ratchet: `tests/core/only-real-asks-need-you.test.ts`, **Working** = a turn runs, or the task's own work goes on without one (2026-11-02, the user: "wait is just acutally waitng, if it is runnig it shoud be i progress"): its current report says working, or waits `own:` (its build, test run, CI run, deploy or land), and its live process, an armed watch or its WAITING clock brings it back (`ownWork`, `carriesOn`; it may stay parked on that trigger), **Waiting** = really blocked outside its own work (a person's review or reply, another task, its lead, a set time, the machine), TODO, an IN_PROGRESS with nothing running (on the user for Main, on its workers, else `stuck`), or snoozed, each row wearing its wait or snooze mark, never the needs ring, **Done** = COMPLETE; a wait reported before that rule (`rule` absent on the report) is asked once again by the reconcile loop. Ratchet: `tests/core/working-means-own-work.test.ts`. Letters, Board choices, errors, triggers and the report only give the words (the ask, on whom or what it waits: another task, a time, a watch, the machine, its lead, not started). The task moves its phase itself: its turn-end self-report (`FOR_USER_*` lines, `readStatusReport` in `session-hooks/builtins.ts`; 2026-10-31, the user: "one light status-only side question" at the turn end, never a four-minute wait: a native Claude Code session is asked only those lines by `src/core/sessions/status-question.ts` once its turn stays quiet 5 s, and the debounced summary no longer asks them; an ACP engine still answers them in the summary; a reconcile loop, `status-reconcile.ts`, every 5 minutes asks again an idle native session whose stored status is older than its last turn end, at most 4 a pass and once per 30 minutes per session, never waking a stopped one) is applied by `src/core/sessions/report-phase.ts` (stopped on the user or waiting on the user = NEED_ACTION, waiting on others = WAITING with the clock it had, carrying on with a live process = IN_PROGRESS, done = WAITING for its leader; Main moves only to NEED_ACTION), never over a move made after that turn ended, never while a turn runs, and a parked task only for a real stop on the user; the leader starts by applying each stored report the same way. A turn a standing routine's fire started (an armed trigger that fired before, none stopped) ends back in WAITING with its clock (`phase.ts`, `task-wait-resume.ts`). A report older than the latest phase move lends its words, never its ask. Walnut's idle reap is not the task's turn (2026-10-27: a worker's queued test runs were detached commands, and the reap killed them after 20 quiet minutes and put the task on the user): it never ends a session whose own work runs on after its turn (a detached background command or an armed wakeup, `workOutlivesTurn`; extended to 24 h, not disabled), and a worker whose session stopped with no report of its own asking the user reads Waiting on its lead, never Needs you (the hand-back still happens, so a reply its lead waits for is settled and an org lead is woken); a task with no lead reads its turn to read (`toRead: 'turn'`). The server derives the status from the phase plus those facts and stores it on the task as `user_status` (`src/core/user-status-sync.ts`, leader only: event-driven, 1.5 s debounce, a minute sweep, writes only on change, never on a COMPLETE row because `updateTaskRaw` would announce the completion again). Every surface reads that one value: the web task rows (`taskNeedsAction`), the Board's Status view (the default view, `BoardStatusView.tsx`, the user's pick of three designs) and its chips, the kanban card line, the Org counts (`org-tree.ts` `userStateOf`), the v1 projection and iOS (`TeamStatusModel.swift`). A task not derived yet falls back to its phase as an older Walnut meant it (`fallbackUserState`, NEED_ACTION = needs). Agent-written words are plain (the `walnut-board` skill forbids codenames and abbreviations), timestamped, and flagged when a day old. A hand-back with nothing asked, of a task with a session that read Working or Waiting, is stored only `HANDBACK_SETTLE_MS` (20 s) after its phase moved (`user-status-sync.ts`; 2026-10-28: 134 of 519 hand-backs were undone by a new turn within 30 s and flashed the Org page red), and a worker whose own trigger is armed reads Waiting on that watch, never "stuck" (`wakeSource`). A snooze is part of that one status (`src/core/snooze.ts`, 2026-10-30, the user: "if something you look at is already snoozed, don't remind me again, unless you have a particular reason"): a start date still to come, the task's own or an ancestor's, turns a status that asks the user into Waiting until that date (`user_status.snoozed`, its held-back ask beside it; a running turn, a live prompt and Main are as they are), and a session's report cannot undo it; nothing reminds about it before then (the re-checks, the status push to its leader, VP and Main, the lead-waits wake, the wait clock's red dot, the Brief's lines), a letter from or about it needs `snooze_reason` (409 `task_snoozed`), and at the date the re-check clocks start from the date. Every reader reads that one value (web `taskUserState` / `taskNeedsAction` in `web/src/utils/session-status.ts`, agents `user_state` and `user_status` in `task_list` rows, `user_status` on every `task_get_bulk` row whatever fields it names, and a summary always with its `summary_at`, because a summary is the note's history and may describe an ask the user answered days ago: `agentStatusView`, `SUMMARY_IS_HISTORY`; 2026-11-02, Main read two answered asks to the user from summaries); `tests/core/task-state-ratchet.test.ts` fails on a new reminder path that ignores the snooze or a new file deciding needs or waiting from the phase, `tests/e2e/task-status-scenarios.test.ts` walks the flows and checks every surface agrees, and `src/core/status-consistency.ts` (op `status_check`, hourly on the primary) finds a stored status the facts no longer give, a snoozed task stored as Needs you, or a park on nothing outside, re-derives the first two and tells the parked task.

## A status change is pushed, and a "needs you" says when it was checked

- **A status change is pushed, and a "needs you" says when it was checked** (2026-10-28, the user: "I've already resolved some of these. You should at least verify ... how can we programmatically let everyone know a task's latest status as early as possible"; Main had read him asks he had done in a terminal as fact). `src/core/sessions/status-push.ts`: when a task's settled user status moves (its state, its ask, on whom it waits; held 90 s, so a turn that ends where it began is no news), one line of Walnut's own record (who, from what to what, when, what it asked the user) goes to every session holding an unanswered request to it (mid-turn, else queued for its next message, never a wake), and to the ONE node right above it (`statusFollowerOf`: a worker's leader, a top-level task's VP, a VP's Main; 2026-10-31, the user: updates go up one level at a time and each node passes on what is news in its own words), running or idle: the line rides that session's next message, never a turn of its own (`status-riding.ts`, one item per task, kept on disk across a restart). A VP and Main follow the tasks that report to them the way a leader follows its workers (`src/core/sessions/org-follow.ts`, 2026-10-31, the user: "a VP must always have its up-to-date status"): at the same edges a worker's leader hears (its turn ended with the task open, it completed, it erred, it waits on the user, it parked), the subtask-notice envelope with its last message (a stop's quote cut to 1,500 characters) rides the node's next message in the same item as the task's status line, so no node hears one change twice (a status line or a lead's team note after a notice already told skips that move, `noticeToldSince` in `status-riding.ts`; a node holding a request to the task hears the request's own notice instead; the store is `cache/status-riding.json`); a top-level task's prompt names the VP or Main it reports to. Anyone may put a watch on a task (`task_watch`, `PUT /api/v1/tasks/:id/watch`, `task.watch`, `src/core/sessions/task-watch.ts`, 10 minutes to 7 days): every status the task gives restarts it, a completion ends it, and when it runs out the reconcile tick asks a task that runs or has a turn its status misses (never one with no live session, an ACP engine or a chat lane) and rides the answer to the watcher. A lead keeps its own tracking per task in its MEMORY.md (`LEAD_TRACKING_LINE`). A leader's own status carries its open subtasks' asks as a list (`user_status.asks`, `rollUpAsks` in `user-status.ts`, at most 12, each with the task it came through), so a VP or Main reads every ask below it from its direct reports, and the Org page's Task view lists a subtask's ask under its top-level task (`topLevelOf` in `org-channels-model.ts`). A session's own ask (`needs`, `source: 'session'`) carries `checkedAt` (its turn-end report or phase move) and `unverified` past `UNVERIFIED_AFTER_MS` (4.5 h); a trigger of the task only adds `watchedAt` (its last run, kept to 10 minutes), never a check, because it watches the task and maybe not this ask (`user-status.ts` `stampChecked`, words in `checkedLine`, mirrored on iOS); `src/core/sessions/needs-recheck.ts` wakes the owning session after `NEEDS_RECHECK_MS` (4 h) to check it itself and arm a trigger when a script can tell (6 in a row while it keeps asking, reworded or not, then once a day, never stopping (2026-11-04, Main's reflection: asks sat NOT VERIFIED 18 hours to 5 days behind a capped count or a watch whose runs counted for nothing; ratchet `tests/core/needs-never-stale-guard.test.ts`), `task.needs_recheck`; a re-check turn's Working is held from the push). A trigger the session armed with `trigger_create watches:"ask"` checks that ask each run (its last check without an error is the ask's `checkedAt`, `checkedBy: check`), and one watching a letter id keeps that letter's re-check quiet while it is armed (`src/core/sessions/recheck-watch.ts`, `task.recheck_watch`), and a re-check with nothing new is answered with the agent-ack line, so the user's chat does not repeat the same status (2026-10-29: one lead wrote the same letter status four times, a 15-minute trigger on it notwithstanding). A request its target handed on (`hands_on`) is never settled by a plain turn end: only a real reply (the target's, or the task that took it over, which may answer it directly) or its deadline (then overdue, still open) (`request-handoff.ts`, `session-send-core.ts` performReply). The self-report's FOR_USER_ASK line asks for that check, the Board, the Org "Needs you" cards, and the phone print the checked line or Not verified, and Main's and a lead's Brief prompt lists the team's live asks with their time (`briefSectionLines`). Ratchets: `tests/core/needs-checked.test.ts`, `tests/core/status-push.test.ts`.

## One decision shows once: tasks of one team asking the same are one ask

- **One decision shows once: tasks of one team asking the same are one ask** (`src/core/same-ask.ts`, `same-ask-tree.ts`; 2026-11-04, a VP's reflection: a lead and its subtask both sat in Needs you asking whether to create three alpha test accounts; then siblings under one lead asked one design decision with opposite picks, and an ask Main had decided still waited on the user). The stored status is made in one place, `statusOf` in `user-status-sync.ts` (the consistency check compares against it too): after `rollUpAsks`, an ancestor whose own ask (a session's question or a Board choice; never a live prompt, a failure, a person's mark or a decision letter) is the same as one its subtree carries up reads Waiting on the deepest task that asks it (`kind: 'task'`, `user_status.sameAsk`), so Home's Needs you, the Org Task view and counts, a VP's or Main's rolled asks, the Brief and the phone show it once. The fold stays while the deeper task still holds the ask (its turn runs on it, it is snoozed with it), and once it asks no more only on evidence the user answered it there (a person's message to it after the fold, `SessionRecord.humanInputAt`, `readFoldEvidence`) and only while the ancestor holds the same report (`sameAsk.answered`; its next status question tells it where the answer went); anything else brings the ancestor's own ask back, so an ask is never hidden on a guess. Teammates beside each other fold the same way (`teamKeysOf`: under one top-level task, or in a project one open lead or VP leads, by `Task.project` or `org_leads`; Main's whole org is no team, nor the Inbox): the older task keeps it (a fixed order, so the row never trades places as their turns come and go; a holder whose turn runs on the ask still holds it), and the other reads Waiting on it (`sameAsk.team`); its status question says to send that task its own pick when it differs, and once the ask is answered there it is told so once (`tellFoldAnswered`). **An ask a lead, VP or Main decided for the user** is sent with `task_send answers_ask:true` (`src/core/sessions/ask-answer.ts`; only from a task it is under, its lead or VP, Main or the person: `409 not_above`; `409 no_open_ask` when it has no ask of its own to answer, naming the task a folded ask shows on, and for a Board choice; an ask of a kind only the user approves (outward, spending, credentials, permissions, cloud_delete, irreversible) needs `user_words` quoting him: `409 user_words`): Walnut leads the message with one line telling the asker (the one time it is told), records `Task.ask_answered`, delivers it only to an open task whose session's CLI is alive, judged on the session the message would really reach (a reply's own routing: past the asker for a carried request, or the asker's live fork) and kept to the write itself (only that session, still live when its row is stored, its stop fence from the check: `liveSendGuard`) (`answerReach`; 2026-11-06, the org reflection: an answer resumed a stopped task, which pushed two commits and armed a trigger: a COMPLETE task, or one with no session running, gets the answer recorded with nothing delivered, `delivery: 'recorded'` with `notWoken`, a request it asked settled by it, and acts on it only through task_start or `force` with a reason; a folded teammate is told only while it runs; the daemon's host never delivers one itself, leaving it to the server, or refusing it while the server is away; ratchet `tests/core/sessions/ask-answer-no-wake-guard.test.ts`, `tests/e2e/ask-answer-no-wake.test.ts`), never against what the user wrote in that task unseen (`src/core/sessions/user-spoke.ts`; 2026-11-07, Main's reflection: Main answered "local only" after his "submit the cr"; the answering task, and a task whose `task_report_set` takes the ask off Needs you, gets `userSaid`: his messages there since the task began asking, `StatusReport.needs_since` kept across consecutive needs reports by both report writers, else his last 3, read from the task's chat (`user-asks.ts`) or an Org node's Threads; one he wrote after the ask appeared refuses the step with `409 user_spoke_since` quoting them until `user_words` quotes each (one check, `settleCheck`, also run by another task's `task_update phase` off NEED_ACTION in both PATCH routes, and counting the words of a teammate whose same ask is folded under it); a close by another task is held (`owed_to_user`) naming his words, and held again when he wrote since; a plain message to a task that still asks shows them beside `openAsk`; the person's own answer is never checked; ratchet `tests/core/sessions/user-spoke-guard.test.ts` fails on a new file that records an answer for him or writes a task's report, `tests/e2e/ask-answer-user-spoke.test.ts`), and `answeredAbove` keeps that ask off Needs you (Waiting, `user_status.answeredFor`) for 7 days while the task asks the same, its next reports repeating it included; a teammate folded under it, or asking it later, reads it answered. Main's and every lead's default instructions say so, and the status question tells every session never to ask what its lead, a VP or Main already decided. Sameness is deterministic and strict, no model call: the same content words in the same order, at least three (`askWords`; a review showed similarity folding "staging" under "production"); the sessions' own word comes first: the turn-end status question (and the summary path) lists the tree's open asks and reads `FOR_USER_ASK_SAME: <task id> | different` (`StatusReport.same_as` / `ask_distinct`; a "different" from either side wins). A report line set from outside (`task_report_set`), a session's `action_required` letter and a Thread an agent hands the user are refused with `409 same_ask` naming the task that already asks it (an open decision letter anywhere in the tree, or a status ask below the writer or in an org node's team; an ancestor's status ask is never a refusal, it folds), unless `same_ask_reason` says why it is another decision; a person's own writes and a host's journal ops are never checked. **One task's ask reworded is the same ask, never news** (`src/core/ask-decision.ts`; 2026-11-09, the CEO's gathering of VP reflections: one ask reworded four times a day, six asks reading as new at every refresh for days, and all five "changes" of one Brief refresh new words with no new fact; the user, 11-07: "can we not ask me everyfucking day"): every ask a task puts on the user carries a decision id (`ask_id` on its report, `user_status.decision`), minted by Walnut and kept on every later report that asks again in any words; the status question shows the session its id (`FOR_USER_ASK_ID: <id> | new`, `FOR_USER_ASK_NEW: <what is really new>`, which counts `ask_rev` up once), `task_report_set` takes `ask_id`/`ask_new`, and only a session's "new", or words that no longer ask it (`sameDecisionWords`: another target swapped in, a "not", another direction or number, almost no shared word), mint another; other options or another way to answer count the revision up by themselves (buttons put on a question he could answer freely, each answering what it asks, or taken off, do not: 2026-11-10), and a Brief refresh tells a revision as the same ask with its new fact, never as another ask. The id only keeps a rewording from being news: the user's words since an ask are still checked on any reworded line (`user-spoke.ts`). News is the decision key (id, revision, option count, the task's due date, the links it points to), never the words, on every path: the status line to the node above (`status-push.ts askNews`), a Brief's moved lines and its refresh wake and hint (`brief-fresh.ts` `n2:` marks), the Needs you changes a refresh tells (`toldDecisions`), the needs re-check count, a stop notice to a VP or Main that was told the decision (`status-riding.ts decisionToldTo`), a thread write that only rewords its ask (no new `updatedAt`), and a watch armed on the ask. Ratchet: `tests/core/ask-decision-news-guard.test.ts` (a rewording corpus through every path; every caller of a "moved" primitive and every file comparing ask words listed from the source), `tests/e2e/ask-decision.test.ts`. Ratchets: `tests/core/same-ask.test.ts`, `tests/core/same-ask-paths-guard.test.ts` (fails on a new caller of `deriveUserStatus`, a Needs you source not listed, a new report writer, letter sender or thread writer that skips the check, a new writer of `ask_answered`), `tests/core/same-ask-team-guard.test.ts` (one org with every relation, the real `statusOf` pass after pass: no two related tasks both show the ask, a new kind of team key fails), `tests/e2e/same-ask.test.ts`, `tests/e2e/browser/same-ask.spec.ts`.
