# Tasks, subtasks and teams

Where work created from a task lands, the brakes on subtasks, leaders and their Board, how a parent hears about its subtasks, and the task phase lifecycle (WAITING included).

_Moved from the root `AGENTS.md` on 2026-11-11; the root file keeps a one-line summary of each rule._

## Work created from inside a task lands beside it (placement, brakes, titles, teammates, leaders and Boards)

- **Work created from inside a task lands beside it** (`src/core/sessions/caller-placement.ts`, enforced in `POST /api/v1/tasks` from the `x-walnut-caller-sid` header): the caller's project and its folder (a new one holding both when it has none; a SUBFOLDER of it holding both when the folder's own OPEN tasks include work that is not the caller or its subtasks (finished tasks, hidden on the board, and work already in a subfolder don't count: 2026-10-07, a leader under a folder of finished tickets nested once per subtask), so the folder tree follows the subtask tree, and the board draws it nested; a folder made for the caller, or found holding only its family, stays that family's home (`family_group_id`), so a newcomer landing in it, a fork of a subtask say, never pushes the family a level deeper: 2026-10-06, five levels), the caller's board tier (a Focus task's subtask is born in Focus; `pinned`/`focus_tier` in the body win), plus the caller's cwd when the caller runs on the project's default host. Whatever a session files is that session's task's SUBTASK (`parent_task_id`; a Worker pill on the board that leads back to the parent, and a `Leader · N` pill on the parent that counts and lists only the OPEN subtasks wherever they live, gone when none is open), in its project, in another one, and from a Personal AI ask too; a subtask in another project takes that project's source and renders as a top-level row there (nesting stays inside one project). Explicit `project` / `group_id` win, but a worker naming a project other than its own task's must say why in `project_reason` (10+ characters), else `409 project_elsewhere` and nothing is made (2026-10-14: a leader guessed a project from its repo's name and filed its subtask outside the team's project); a folder never follows work into another project; only WORKER callers are placed from (the Personal AI's asks, born `walnut_agent` or filed under an `Ask …` project, keep the old defaults for project, folder, tier and cwd and get the parent link alone; humans and replicas keep the old defaults entirely). `GET /api/v1/me` says who the caller is and where it stands.
  A start from a worker takes the caller's host + cwd as ONE pair when the task has no place of its own, and `task_list` from a worker defaults to the folder ring (project when no folder).
  Server brakes, never prompt-only (`src/core/sessions/subtask-limits.ts`): a session's subtask sits at most 3 levels below a top-level task (`409 subtask_too_deep`), and no lead caps how many of its subtasks run: each host has its own slots for automatic starts (`src/core/sessions/host-admission.ts`, one per two CPUs and per 3 GB of memory or `session_limits`), and a worker's start naming no host or folder waits explicitly for a free slot when no suitable host has room, then starts automatically (2026-11-11). A start naming its host or folder still fails with `409 hosts_full` when full. A waiting answer says `started: false` with `queued`, never that it started. A task asked to start or sent work that shows nothing for 10 minutes tells its asker (`session-request-notify.ts` remindSilent). The human and an ask are never limited.
  **A session's task title is a few words** (`src/core/sessions/task-title-brake.ts`, in `POST` and `PATCH /api/v1/tasks`): over 60 characters from any session caller, the title is cut to its head at once (the long form becomes the description when the create had none) and refined in the background by the fast model with the session-title recipe, written only while the task still wears the cut. Humans and the phone (no caller header) are never touched. The prompts also pin two words: a "subagent" is Claude Code's Agent tool, a "subtask" is a Walnut task (2026-09-30: "use a subagent" was answered with a Walnut subtask carrying a 140-char title).
  **A subtask is a teammate, not a step**: it owns one area with a clear goal; one per ask (the session asks the user before splitting), and more work in its area goes to it with `task_send`. Prompt, `task_create` description and skill say so; the nudge is server-side: every create that makes a subtask returns the caller's other open subtasks in `placement.open_subtasks`, and the op outcome names them (2026-10-01: one "use a subtask" ask became one task per sentence, then a fourth for the third one's follow-up).
  **A leader adopts, and keeps a Board.** An existing task becomes a worker through `PATCH /api/v1/tasks/:id { parent_task_id }` (`task_update`; `""` releases; on the board, the Leader flyout's "Adopt…" and the task kebab's Team row, collapsed by default (2026-10-05: rare, so one row that expands on click), holding "Adopt a worker…", "Release a worker…" (a leader lets one go; it keeps running) and "Leave leader"): the server checks the parent exists, is not the task or one of its descendants, and, for a session caller, that the adopted SUBTREE still fits `MAX_SUBTASK_DEPTH`; humans are never limited; project and folder stay put; the adopted task's session is told through `walnut-notify` only when it is MID-TURN, where the notice rides along for free; an idle one is never woken for bookkeeping (2026-10-02: five idle workers each woke to say "this is only a notice"), it reads the link from its task when it next runs (its prompt line about its leader is built at spawn). Every task may carry a **Board** (`src/core/boards/`, `src/web/routes/board-v1.ts`, ops `board_get/set/edit/post/post_delete/project_set/remind`, skill `walnut-board`, the `Board` tab beside Files and Changed): one HTML document the leader writes and any task in its tree may edit (exact-string `edits`, each `old` once, all or none; a version for optimistic writes), stored at `WALNUT_HOME/boards/<taskId>.json` with the chat threads and the user's marks beside it, rendered in a sandboxed `allow-scripts` iframe (no same-origin, CSP) with Walnut's runtime upgrading `<walnut-task>` (live chip), `<walnut-thread>` (a human's message is stored and delivered to the task's session like a human `task_send`; the session answers with `board_post`), `<walnut-mark>` (the user's note), `<walnut-strip>` and `<walnut-unread>`; beside the html Walnut also keeps the board's projects (one area of the board each, not a Walnut project; their status, set with `board_project_set` or picked by the user on the `<walnut-project>` pill, recolors every `data-project` element; a session's write keeps the user's pick unless it passes `override_user`, 409 `status_set_by_user` otherwise), the user's read ticks on `<walnut-check>` points (the server hashes each point's html, so an edited point comes back unread), the user's answers to `<walnut-choice>` (an option, their own words from the same docked composer as a thread's, or both, delivered to the session as one message like a thread message), reminders on a choice or a thread (a server clock, `board-reminders.ts`, modelled on `task-wait-until.ts`), and the sections the user has seen; ticks, answers and seen sections record who made them, the user or an agent (`by`), and an agent's shows as such. A team shares ONE board (`resolveTeamBoardTask`: the nearest ancestor with a board, else the root; `?team=1`, `/board/owner`, and every `board_*` op's default); `board:changed` carries a top-level `taskId`. The leader hears about the Board at spawn when it has open subtasks and in every `task_create` outcome that lists its team (2026-10-01: a user could not follow 40 workers through the leader's chat and had the leader hand-write exactly this page as a local file, whose chat never reached the AI and whose marks it could not read).

## A parent always hears when its child stops (and about its subtasks by their state)

- **A parent always hears when its child stops** (`session-request-watch` in `src/core/session-hooks/builtins.ts`): a pending reply request is settled with a Walnut notice when the child's task lands NEED_ACTION or COMPLETE (a COMPLETE set mid-turn waits for that turn's end, so a reply later in the turn still wins), and the notice quotes the child's last message (≤4000 chars, framed as data) plus the tool calls it made after that message (a child that closes its task often ends the turn without a word), so a child that forgot to reply still hands its result over. **A session that completes its own task is stopped when that turn ends, not at once** (`src/core/sessions/self-complete-stop.ts`, keyed on the complete's `actorSid`): stopping it at once cut the very Bash call running `task_complete`, which the CLI records as "The user doesn't want to proceed with this tool use", along with its closing words (2026-10-05). That turn's summary skips the debounce and the stop waits for it (`awaitFinalSummary` in `src/core/session-hooks/builtins.ts`, at most 3 min), because a stopped CLI cannot answer the self-report and a completed task has no next turn; a completed task's summary only records, it notifies no one. A turn end that another turn follows within 3 s is not the end (a background command that finishes later leaves the session idle for about 0.1 s before the CLI's follow-up turn), so the stop waits for that turn. Its other sessions, and a completion from the board or another task, still stop at once. **Never to the session whose own API call made the edge**: the phase event carries `actorSid` (the `x-walnut-caller-sid` of the PATCH or complete), a request that session holds is settled without a notice, and a parent whose session acted gets no subtask notice (2026-10-02: a leader completed 16 workers and was woken 16 times to read the summaries it had just read).
  **A parent hears about its subtasks by their STATE, not by who talked to them** (`src/core/sessions/subtask-notices.ts`, same edges, same hook): whether or not it holds a request, a parent's session gets a `kind="notification"` envelope (no `request` attribute, `outcome` = `stopped` | `completed` | `error` | `blocked` | `waiting`) when a direct subtask's turn ends with the task still open (the body names who started that turn: the user, the parent's message, a trigger, another task), completes, errors, waits on a human prompt, or parks itself. 2026-09-30: a child's one request was answered, so its parent heard nothing more and lost it. One voice per edge (the request fallback speaks for a parent that is an asker; a child that answered its parent within 10 min is not reported "stopped", and its completion carries no quote); one message per parent per 3s burst, several envelopes inside; a newer `stopped`/`blocked`/`waiting` for the same child replaces the one still queued (stable id `sn-<child>-<kind>`); a COMPLETE parent or one with no session hears nothing; direct parent only; the child hears nothing back, so there is no loop. Delivery is the reply's path (`deliverToSession`, source `walnut-notify`, never reopening): a busy parent gets it mid-turn; a parent whose turn is over (idle, its task in NEED_ACTION) is woken only for `completed` and `error`, and a STOPPED parent session is never woken (2026-10-01: a task that had finished its own work was woken, and billed, every time the daily digest it once filed ended a trigger turn; a blocked worker needs the user, not its leader). It reads the rest when it next runs (`open_items`, `task_get`, its Board's live chips), and a reply it waits for (the request fallback) still wakes it. Every `completed` notice says how many of the parent's subtasks are still open and names them (`src/core/sessions/subtask-batch.ts`), and an idle parent is woken ONCE for a batch: a completion while another subtask still works is held (on disk, `subtask-notices-held.json`) and goes out with the edge that leaves none working, an error, or the parent's next turn (2026-10-28, the multi-agent tracking research). A reply or a completion may carry `result` / `evidence` / `not_done` (`src/core/peers/structured-reply.ts`, stored as `Task.result_report`); a non-empty `not_done` reads as Partial on the Board, the Brief, the phone and the parent's `open_items` until it is settled (`task_not_done_settle`). A request past its deadline stays OVERDUE, STILL OPEN (status `expired`, listed in `open_items` and the Brief ask's Needs you list) until a reply settles it, with one reminder to the asker at twice the deadline. A session completing ANOTHER task that is still in use (`source-in-use.ts`: a person wrote in it, its session was open in a terminal, an org role, an armed trigger) or unfinished (`complete-in-use.ts`: a Partial nobody settled, someone else's unanswered request, a turn running now) gets `409 task_in_use`, through `POST /complete` and a PATCH to COMPLETE alike, unless it passes `force` with a `reason`; open subtasks never block it. **One step stops a whole team** (`src/core/sessions/team-stop.ts`, ops `team_stop`/`team_resume`, the Board's Status view and the task kebab's Team row, the phone's Team menu): every open task under it has its live sessions stopped (never the caller's), its armed triggers paused and its wake clocks taken off, recorded on the root as `task.team_stop` so a resume turns exactly those back on; `when:"turn_end"` lets a running turn finish, and the parent hears no "stopped" notice for it. `sessions:"keep"` pauses only those wake sources (every routine aimed at the team, trigger or plain cron, and the clocks) and stops no session; `trigger_list` with `task` (and `team:true`) lists them first (`GET /api/v1/tasks/:id/wake-sources`; 2026-10-29: Main grepped the routine list to find what would wake a team during the user's meeting). **A session ending a turn while it holds a request it has not answered is told before the turn closes** (`src/core/sessions/unanswered-at-stop.ts`, the CLI's own Stop hook in every session's `--settings`, `src/providers/stop-unanswered-hook.ts`; 2026-10-29: workers ended a requested turn with "No response requested"): the hook's `block` answer names the request and the reply command and the CLI goes on in the same turn; once per turn (`stop_hook_active`), at most `MAX_NUDGES` turns per request, never for a request handed on, one not delivered yet, an asker whose task is complete, or a turn whose own work runs on (`workOutlivesTurn`); `WALNUT_STOP_UNANSWERED=0` turns it off. An overdue notice of a request handed on quotes the task it went to (its latest message and state), never the target's own unrelated message. **A parent completes with its subtasks still open** (2026-10-04 user call: a leader whose worker was a recurring daily job could not be closed at all; the old `409 active_children` guard is gone, for humans and sessions alike). The subtasks are not touched: they keep running and keep their parent link, and `POST /api/v1/tasks/:id/complete` lists them in `open_subtasks`. A COMPLETE parent hears nothing more from them until it is reopened, and a reopen restores it all: no state notices (also not one in the 3s window), and the ones already queued for it are dropped at completion; no request fallback (a Walnut notice never goes into a COMPLETE asker's session); its pending asks to them become `withdrawn` (`quietCompletedParent`; `restoreWithdrawnAsks` puts them back on reopen); a reminder a session set on its Board waits; and a subtask's own `task_send` or reply to it is refused with `409 parent_complete` (`session-send-core.ts`, mirrored by the daemon's offline host), because a peer message would reopen it. Anyone else's message still reopens a completed task.

## Phase lifecycle and WAITING

- Phase: `TODO` → … → `NEED_ACTION` → … → `COMPLETE` (an agent may set any phase, COMPLETE included: a parent that checked its subtasks' work may close them). A new message from a human or a peer task into a completed task's session reopens it to `IN_PROGRESS`; a session's message or answer to a COMPLETE task is first refused with `409 target_complete` (the task is done, read its result) and goes through only with `force` and a `reason`, which leads the delivered text (`checkCompleteTarget` in `src/core/peers/envelope-kit.ts`, shared by the server and the daemon's offline host; 2026-10-14, the user: "not a hard no, there must be a valid reason") (`session:input` with an allowlisted send source is the one path past the terminal guard, see `sendSourceReopensTerminal`); late results, hints and automated sends (auto-continue, routines, hooks) never do. `WAITING` (`src/core/phase.ts` `HELD_PHASES`, timer in `src/core/task-wait-until.ts`) parks a task until something happens: it stays in its board tier (the `wait` tier, labelled Parked, is a shelf, not a state) but leaves the default task list and tier cards (`showWaiting` in `TodoPanel`, revealed by "Show waiting" or a WAITING phase filter; search always finds it); nothing of the turn that set it moves it, whoever set it (its output, its end, a session error, the reconciler, a background agent coming back inside it: that `{running}` keeps the turn's `turnStartedAt` and is skipped as `held-this-turn`; a turn-start with no generation, the 30s snapshot pull, is never a new turn: `held-reconcile`, both in `applySessionPhase`), except a prompt that blocks on the human (NEED_ACTION); ANY new turn (a trigger fire, a human, a peer, the `wait_until` clock, which wakes the session with a `kind="trigger"` note or hands a sessionless task back as NEED_ACTION) moves it to `IN_PROGRESS`; a turn that only interrupted the wait (a peer's message, a Walnut status notice, the CLI's own follow-up for background work that came back) ends back in WAITING with the same `wait_until` while the task still has an armed trigger, none stopped and none fired since, unless something it waited for or a person came on the way (any send that is not an interruption: a person's, a fire, the clock, a reply to its request, a subtask's completion or error (`endsWait` on the send), a Retry), a prompt for the human, an error, or a phase write;
