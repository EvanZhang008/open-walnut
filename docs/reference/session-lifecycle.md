# Session lifecycle rules

What happens to a session across restarts, full contexts, compactions, lost answers, unreachable hosts and moved folders, and what a running session is told when its task or its rules change.

_Moved from the root `AGENTS.md` on 2026-11-11; the root file keeps a one-line summary of each rule._

## Parse harness-owned data the harness's official way: never invent Walnut-side bookkeeping on top of a file Walnut doesn't own

- **Parse harness-owned data the harness's official way: never invent Walnut-side bookkeeping on top of a file Walnut doesn't own.** If the CLI/agent already defines the format's semantics (e.g. transcript JSONL is a `parentUuid` tree and the CLI chain-walks to the active leaf), port that exact logic. Offsets/fingerprints/side records reinterpreting someone else's file go stale the moment the owner writes in a way Walnut didn't initiate. Walnut-invented logic belongs only in Walnut-owned formats (stream capture, ACP journal).

## After a restart, Walnut resumes the work a restart interrupted, and only that

- **After a restart, Walnut resumes the work a restart interrupted, and only that** (`src/core/session-auto-recover.ts`, rules in `src/core/sessions/restart-loss.ts`). 2026-10-26: the Mac rebooted with 42 sessions on it and none came back; twelve tasks with work in flight were handed back as NEED_ACTION, as if they waited on the user (the old per-host budget of 10 went to tasks already handed back, and the daemon's snapshot then rewrote each record's `status_reason`, so the few armed recoveries read as "not infra"). Now every session the startup reconciler (or a runtime site: host reconnect, health monitor) finds killed gets a durable `restartLoss` on its record, a field no status write touches, decided from recorded facts, never a time threshold: the daemon's fold of its stream file at death (an open turn, background commands, an armed ScheduleWakeup or /loop cron, an open permission prompt), else its last projected status, plus the task's phase. Resumed: IN_PROGRESS or WAITING with work in flight (a WAITING task whose wait rode on its own background command or timer waits for nothing). Not resumed: an open permission prompt or a settled turn (handed back, truthfully), WAITING on a clock/trigger/peer (left parked), already NEED_ACTION/TODO/COMPLETE, a working directory the reboot removed (handed back with a note). While a loss is undecided or queued, every hand-back path (`handBackTaskOnSessionEnd`, the snapshot's settled hand-back, the health monitor's drift rule) asks `holdsHandBack` first and leaves the phase alone. The queue: open turns first, then the most recent work; per host `WALNUT_AUTO_RECOVER_CONCURRENCY` (2) resumes in flight, a stagger, and a load gate on this machine (`WALNUT_AUTO_RECOVER_MAX_LOAD` 3 per CPU, then one at a time after 5 min); the attempt budget (3 per 6 h) and the loss are persisted, so a reboot loop stops and a restart mid-recovery resumes the queue; an offline host keeps its sessions queued for up to a day. Each resume is ONE `sendMessageToSession` (the daemon's one-CLI-per-session guard covers it), and the restart note (`sessions/restart-notice.ts`: the cause, what was lost, /tmp cleared on a reboot, whether the cwd survived, check state first) rides in front of whichever message reaches the session first, a human's or a peer's included, once. A death a daemon reports is taken on BEFORE it is written (`sessions/restart-death.ts`; 2026-11-04: a remote host rebooted under 8 running sessions, and the reconnect pull wrote each death and handed the task back before recovery was asked, so it read NEED_ACTION and resumed none): a snapshot apply and the legacy reconnect relabel call `noteRestartDeath` first when the death has a witness (found across a reconnect, a daemon that started after the session was last seen, or a record already marked unreachable), and `applySessionPhase` holds every NEED_ACTION death edge of a held session, a record that reads live included when the edge reports the death itself (`processAlive: false`: a runner the server had attached reports its dead process as a turn end and rewrites the record live, so `fire()` asks the host's fold before it takes a live-reading record for resumed). Opt out: `WALNUT_AUTO_RECOVER_ENABLED=0` or `hooks.overrides['session-auto-recover'].enabled: false`.

## A session never stays stuck on "Prompt is too long"

- **A session never stays stuck on "Prompt is too long"** (`src/core/sessions/context-full-recovery.ts`, `context-full.ts`; 2026-11-05: a host with Claude Code's auto-compact off reached the CLI's hard stop, 200K window less 23K, at 88% on the badge, and every message after it, the user's "hi" included, was refused before the model; the banner offered only Reconnect). A turn that ends with that error gets its session compacted by Walnut (a quiet `/compact`, `context-compact`), then one note (`context-recovery`) hands the session the messages that got no answer, word for word. At most 2 such compactions an hour start by themselves; past that, or when a compaction fails, `contextRecovery.state: 'failed'` and the banner's Compact and resend (the Retry route, which compacts for this error, or for any error while that state is failed, from any surface: `needsContextRecovery`) runs it again. One recovery holds a session from the overflow to the resend's send, both sends are bound to the stop fence of the overflow, and a Stop or a completed task ends it with nothing sent. While it holds a session, its turn is not over to any reader: `turnHold` (so every TurnEndWait user) reads it mid-turn, a triage run is settled only by the turn that answers (or as the error, once the recovery fails), and a notice never quotes "Prompt is too long" as the session's answer (`noticeText`; 2026-11-06, an asker read it as the reply). Claude Code's own error reply (its synthetic message: `isApiErrorMessage` in the transcript, `error` on the stream line) is an error row, `Claude Code: Prompt is too long` (`cliError`, live and in history), never the assistant's answer, and stands on its own row (2026-11-06). A compaction a restart caught keeps the session held and its turn quiet: the owed messages live on the record (`contextRecovery.owed`), the host's transcript is read for a compaction after the overflow (by order, not by clock), the resend waits for the turn to end and is bound to the stop fence of boot, and a Stop meanwhile ends it with nothing sent. With auto-compact off (the CLI's own `isAutoCompactEnabled` in its get_context_usage answer: settings, the legacy ~/.claude.json and the environment alike) the context percentage is measured against that hard stop (`stopsAt`, `contextStopsAt`), so 100% is where the session stops. The window itself is one rule (`resolveContextWindow` / `modelStringWindow` in `src/providers/context-window.ts`, its web twin `sessionContextWindow`; 2026-11-06, the user's Mac app read "Context 324.4K / 200K (162%)" on Opus 5.5): the CLI's own reading wins; a model the model catalog marks `native_1m` reads 1M with no `[1m]` in its id; every other answer is lifted to what the session shows it holds (its tokens, the CLI's effective window), a Claude model to 1M; a stored window counts as the CLI's own only when the record says so (`modelMaxWindowSource`) for the model it runs (`modelMaxWindowModel`). The model list shows one row per model (`oneRowPerModel`, iOS `ModelCatalogRowLabel.oneRowPerModel`). Ratchets: `tests/core/sessions/context-full.test.ts`, `tests/core/sessions/context-full-turn-end-guard.test.ts` (fails on a new turn-end listener that completes a task without asking the recovery), `tests/e2e/context-full-recovery-e2e.test.ts`, `tests/e2e/browser/session-context-full-banner.spec.ts`, `tests/core/context-window-sites-ratchet.test.ts` (fails on a new file naming a window by number).

## Right after a compaction, a session reads back what is still open

- **Right after a compaction, a session reads back what is still open** (`src/core/sessions/open-items.ts`): every Claude Code session is spawned with the CLI's own SessionStart hook (matcher `compact`, `src/providers/compact-open-items-hook.ts`, in the same `--settings` arg as the env), which runs `walnut tools call open_items '{"hook":"compact"}'` and puts the task's unfinished direct subtasks and its pending reply requests (both ways) into context, with no extra turn. A summary is the model's own writing: on 2026-09-30 one dropped a subtask still waiting on a review, and the parent then treated that work as nobody's. Nothing open = nothing injected; the command never fails (no error row); `WALNUT_COMPACT_OPEN_ITEMS=0` turns it off.

## A task keeps the user's unanswered messages, not its summary

- **A task keeps the user's unanswered messages, not its summary** (`src/core/sessions/user-asks.ts`, model `user-asks-model.ts`; 2026-11-03, the user, translated: "why do you miss things?"; a worker told his question "I'll check first, then get back to you", two compactions dropped it, and its lead's team note had counted it answered because the worker's turn ended after it). Every message a person types into a task's chat (and a letter answer's note) is filed on the send path at `WALNUT_HOME/user-asks/<taskId>.json`; Main and the VPs keep Threads instead. The turn-end status question lists the open ones and asks `FOR_USER_OWED` (the ids still owed: "on it" is owed; an answer, a delivered result or what he needs to decide, a plan or a question back to him, is not, even while work it started goes on), and Walnut closes the rest; a completion closes all, a week expires one. They lead the post-compaction readback, ahead of everything else, followed by his words of the last two days that were answered (`recentWordsReadback`; 2026-11-03: three compactions thinned a night's conversation to one line, and every message of it had been answered), and `task_history` pages back with `before` (its `older.before`) to read the rest; owed 30 minutes, the Stop hook names them (twice at most, never while the work runs on or the task parked) and the lead's team note lists them in his words; owed an hour with no turn running, the session is woken once. Those three (the lead's note, the Stop hook, the wake) read one value, `owedAsks`: an ask the task's status handed back to him after he wrote it (`handedToUser`: a live prompt, letter or Board choice waiting on him, or a needs or answer-to-read status the task reported since; never a failed, machine-stopped or limited session) is owed to none of them (2026-11-10, a VP's reflection: a dry run with "start with this plan?" and a delivered test run stayed in the lead's "Owes the user an answer" for 6 to 13 hours). `WALNUT_USER_ASKS=0` turns the loop off. Ratchets: `tests/core/sessions/user-asks-ratchet.test.ts` (every path that files an Org node's thread files the ask for other tasks), `tests/core/sessions/user-asks-answered-guard.test.ts` (replays both 11-10 cases; no reader outside the model reads `owedAt`), `tests/e2e/user-asks.test.ts`.

## An op call whose answer is lost says what is known, and a resend runs it once

- **An op call whose answer is lost says what is known, and a resend runs it once** (`src/lib/op-call-id.ts`, `src/ops/op-calls.ts`; 2026-11-04: `task_send` came back `hub_timeout` while its message was delivered and answered, so the caller could resend it, two copies, or take it for lost). Every client picks one call id (`oc-…`) per op call and sends it beside the op's name (`callId`, outside `args`, so an older server ignores it): the `walnut` CLI on every host, its MCP server, the source daemon's CLI, the Mac's CLI and MCP server, plugin jobs, and the offline handover's replays of a host journal (`journalCallId`). The server runs a write op once per id (a copy waits for the first, or gets its answer; another op or other arguments under the id is refused), and each write the call makes to its own API carries `x-walnut-op-id` derived from it (`writeOpId`: call id, route, order), which the applied-ops ledger dedups across a restart. A call whose write lost its answer, or was refused with a 5xx, 408 or 429, is not kept: its copy runs again and the ledger answers what already applied. A lost answer prints the call id, the read (`op_result`, `GET /api/v1/op-calls/:id`: running, done with its answer, lost with its writes, applied, unknown) and the safe re-run: the same arguments with `"_call_id"`, which clients and `executeOp` take out before the op's arguments are checked. A poll that is a write (`approval_wait`, `password_wait`) gets a new id each time. An answer holding a secret, or over 256 KB, is never kept (its copy runs again and meets the route's own checks), a copy from another session under the id is refused and `op_result` shows the answer only to the calling session; a self-call whose body was cut short counts as lost, and so does one a handler caught and answered ok over (the bulk ops); a host daemon derives a same-host `task_send`'s message id from the call id (`messageIdOfCall`), so a re-run is one delivery; a handler that fails on its re-run after an earlier try already wrote (a `note_edit` whose edit applied) says so, naming those writes. The server's own lost self-call answers the gateway `hub_timeout`, so every client prints the lines above. Ratchet: `tests/mcp/op-call-id-ratchet.test.ts` (every `tools.call` client and `executeOp` caller, every write op's write path).

## A message to a host nothing reaches waits for that host, and says so

- **A message to a host nothing reaches waits for that host, and says so** (`src/providers/host-wait-words.ts`, `claude-code-session.ts` `linkDownHost` / `armSlowHostRetry('link')`; 2026-11-06: the Mac's sign-in to a dev host expired, and a person's messages to tasks there read "Send failed: Not sent yet: waiting for the connection to the session host" with no host and no next try, a bare "Queued" after a reload, and nothing in the panel). Every runner path that ends a delivery asks whether the session's host link is down (the error says nothing reached the host, `isHostLinkFailure`, or the pool says the link that was up dropped, `hostLinkDown` in `daemon-connection.ts`): its rows stay pending under "Not sent yet: Walnut cannot reach <host's name> right now ..." with the next try (the host's own re-dial, `hostReconnectAt`, or a clock that never dials a host still down) and Send now, never "Send failed"; the reconnect delivers them (`redeliverPendingForHost`). A reloaded panel reads the same words and next try (`session:get-queue` `heldReason`/`heldRetryAt`, `core/sessions/held-wait.ts`, which after a server restart reads the wait from the link itself). The session panel says the host cannot be reached once a re-dial has run 10 s (`SessionHostDownBanner`, `HOST_DOWN_GRACE_MS`; at once for a failed or switched-off host; 2026-11-11: drops a relay ended and the link answered again in 3 to 5 s blinked it 14 times in 30 minutes), a column reads its history again when its host comes back (a reply written meanwhile), and the task reads Waiting on its machine, naming the host, on every surface (`user_status` `hostDown`, re-derived on each `host:status` link change). Ratchets: `tests/providers/delivery-link-down-ratchet.test.ts` (every runner function that puts rows back or reports them failed is classified, every transport `SendHeldError` is classified), `tests/providers/host-link-down-delivery.test.ts`; E2E with the link cut on purpose: `tests/e2e/browser/cloud-host-link-down.spec.ts`.

## A host whose link keeps dropping reads unstable, never "Connected"

- **A host whose link keeps dropping reads unstable, never "Connected"** (`src/providers/daemon-link-drops.ts`, `hostFlapOf` / `hostConnectedWords` in `src/core/hosts/host-problem.ts`; 2026-11-08: a laptop on the host network dropped every 30 s for hours and read Connected between drops). Each drop of a link that was up (not a planned daemon swap or a teardown) is kept for an hour and rides the `host:status` frame as `drops`; 3 in 30 minutes reads "Unstable: its link dropped N times in the last 30 min" on the Settings row, the host dot, the bell's host row and card, the fleet card (`connection.unstable`, a Link unstable problem) and `host_list` (and no place for a long-running job). Over SSH the bulk channel has a connection of its own, and every upload no person waits on (a copy's chunk, the replicas, the notes' pictures, the host's whole read copy sent `bind: false`, `host-slice-unbound-v1`) rides only that one, failing with nothing sent while it is down (`BACKGROUND_UPLOADS`): a relay ends an SSH connection a few MB up, and the read copy pushed on the session link after each reconnect was 14 drops in 30 minutes (2026-11-11). The "connection lost" log line names the bytes each command sent on the session link (`mainUploadSummary`). Ratchets: `tests/providers/bulk-uploads-guard.test.ts`, `tests/providers/daemon-connection-bulk-own-link.test.ts`. Ratchet: `tests/core/hosts/host-connected-words-guard.test.ts` (every file that says "Connected" reads the rule or is listed as no host link); E2E: `tests/e2e/browser/cloud-host-flapping.spec.ts`.

## task_history reads short when asked

- **task_history reads short when asked** (`src/ops/task-history-shape.ts`, applied in `src/ops/work.ts`; 2026-11-02, Main's daily reflection read one task's history as about 90,000 characters, over its tool output ceiling): `compact:true` keeps every message's text and folds each tool call, thinking block and Walnut status notice to one line (the person's own words, `personText` included, are never clipped; an assistant reply clips at 2,000 and another session's note at 1,200), `limit:N` keeps the newest N text messages (the route's `visible`, so the page reaches back for them; the cut never splits rows sharing a timestamp, so `older.before` reads the rest), `since:<ISO>` keeps rows after a time (the route's `since`; a cut page that starts after it asks the page before whether `since` was reached). The route honors `visible` and `since` only on a page it builds, so either one sends `fresh=1`. A shaped answer carries `left_out` (counts and characters dropped, one `note` line); with none of the three the answer is the route's own, unchanged. `tests/mcp/task-history-compact.test.ts` pins a 100-row heavy page under 50,000 characters compact.

## A session hears where its task stands now when that moved

- **A session hears where its task stands now when that moved** (`src/core/sessions/place-notice.ts`, called from `sendMessageToSession`): the prompt names the task's project, folder and leader at spawn, but every cold resume replays the spawn-time prompt byte for byte and a live CLI never rereads one, so a task the user moved kept a session that believed the old place (2026-10-14: a leader moved a week earlier still read its old project in its prompt and filed its subtask there). The told place is background state (`placeNoted` on the session record, valid while it runs on the prompt it was written against, else the place read back from the stored prompt, else the record's start project); when the live place differs, the next message into the session carries a `kind="notification"` `outcome="moved"` note in the same queue row, so it costs no turn and never interrupts one. A compaction keeps the system prompt and summarizes the rest, so a note may be gone afterwards while the prompt's old place stays: the stream's compaction boundary (`lastCompactUuid`) voids every earlier note, and the post-compaction `open_items` hook states the live place whenever it is not the prompt's, which counts as told (the way Claude Code re-attaches its own state after a compaction instead of trusting the summary). Personal AI asks are never told.

## A running session hears its default instructions that changed

- **A running session hears its default instructions that changed** (`src/core/sessions/instruction-notice.ts`, 2026-10-27; the user: a rule change reached Main only at its next fresh start, and a session older than the charter brought the old ways back after every compaction). A resume replays the spawn-time prompt byte for byte, so it never picks up a change, except a cold resume whose prompt cache has expired, which runs on the current prompt and stores it, since the replay would save nothing (`src/core/sessions/prompt-refresh.ts`; 2026-11-06: a VP on a 3 KB prompt from 2026-10-24 was told 28 KB after every compaction), and a refresh that costs less than restating the debt (`refreshPays`: the rewrite against the restatements of about a week of compactions for Main, a VP or a lead, one for any other session). A busy node never reaches an expired cache, so after a compaction, once its turn ended and it stayed quiet 20 s with nothing running in its CLI, Walnut respawns it with no turn on the current prompt, keeping the conversation (`src/core/sessions/prompt-refresh-respawn.ts`, decided once per compaction in `promptRefresh`; 2026-11-11: the Walnut VP was still told about 33 KB after each of its 4 to 6 compactions a day). `defaultInstructions(task)` in `session-context.ts` is the prompt without its state lines (title, place, leader, workers, task directory); every line of it the stored prompt lacks is a changed rule. The first line frozen into the session after that carries a `kind="notification"` note with only those lines (under their heading), once per prompt and compaction boundary; a later change sends only its own lines (told lines kept as hashes in `taskRoutingNoted.lines`), the post-compaction `open_items` hook restates them all, and a current prompt hears nothing. Few and small (2026-11-03, the org reflection: 64 notices, about 287K characters, in 12 hours across 100 sessions): once told on a prompt and boundary, the next notice waits `NOTICE_GAP_MS` (3 h), so changes close together go out as one; it rides only a line with a person's, a task's or a trigger's message in it, never one of Walnut's own notes alone (`isWalnutNotesOnly`); a fork's compaction (a side question) runs the hook too, and its statement keeps what it replaced as `prior`, which still counts when the statement is void (`heldStatement` in `hook-statement.ts`; it had wiped the record, and the next message restated everything, 10.8 KB twice in 20 minutes), for the place note as well; a hook statement takes the boundary the record holds under its lock; and the hook adds at most `HOOK_CONTEXT_MAX` (9,500) characters, because Claude Code shows the model only a 2 KB preview of a hook's text past 10,000 (Main's 39 KB statement was recorded as told): changes that do not fit come whole in front of the next message instead. A versioned block (the user's profile, a Main's or lead's core instructions) is compared by its words against the version the session holds (`instruction-diff.ts`; 2026-10-30, a one-line USER.md save re-sent the whole 4.9 KB profile to about 25 sessions): only the new or reworded lines, each under its sub-heading, and the removed ones; a session that never had the block, or whose block changed form, gets it whole; a change is never sent whole (2026-11-03: a save that reworded 10 of 27 lines went whole to every live session), a removed line is named by its first 80 characters and a reworded one says its new wording is above. A line USER.md's 4000-character budget leaves out is still the user's and is never told as removed (2026-10-30: two rules still in the file were told "no longer in force"); a change to a block that does not fit says so, and a save past the budget answers with a `warning` naming what is left out. One notice is on its way to a session at a time (`instruction-notice-flight.ts`), a delivery records what that notice said onto the record as it is then, and the daemon writes one notice into one CLI process once (`noticeOnce` in `daemon-core.ts`), because the server's queue and the host's own same-host delivery each learn of the other's only later (2026-10-30: Main got one twice, 4 s apart). Every Claude Code task session gets it, Main, leads, workers and Personal AI asks alike (an ask's persona text is not compared, only its Walnut session context); a prompt without the Walnut identity line (a slim profile) and ACP engines never do: Codex rebuilds its developer instructions at each process start, and other ACP engines read it once per new provider thread. The wire names stay `outcome="task-routing-policy"` and `taskRoutingPolicy`/`taskRoutingDue` in the host slice, from when it carried only the routing rules: the web and iOS timelines and older daemons read them. The user's profile and standing rules ride those default instructions too (`src/core/sessions/user-profile-context.ts`, 2026-10-28; Main recorded the user's rules in memory/USER.md and only the Personal AI's persona read it, so the user repeated one): every task session reads USER.md's sections last in its prompt, under `## Your user`, after the memory safety screen (an entry it holds back becomes a line that asks no session to act) and with the words capped at 4000 characters. Each line carries a version of the words and of when they were saved, so any save, an undo included, reaches a running session as what changed from the version it holds, and an emptied file says none are recorded now; the companion reads the Mac's copy (`companionMemoryDoc`), never its disk. A persona leaves its own copy out when the session's Walnut context carries it (`userInSessionContext`: a native or ACP ask, a lane of an ask task, the drift repairs only when the stored prompt is Walnut's), and the companion's chat lane keeps the persona copy the Mac rendered.

## Every task has a working directory that survives reboots

- **Every task has a working directory that survives reboots** (`src/lib/task-dir.ts`; 2026-10-25: a restart emptied /tmp and took several tasks' clones, one task's only copy of an unmerged commit, and kept evidence). The host's daemon makes `${XDG_STATE_HOME:-~/.local/state}/open-walnut/tasks/<taskId>` when it starts a session for the task (both twins, the ACP start too; capability `task-dir-v1`, sidecar `task-dir-core.cjs`) and sets `WALNUT_TASK_DIR`; the prompt names it, and the rule (`WORK_PLACE_RULE` in `src/core/work-place.ts`) rides the session prompt, the operating contract, the `walnut` skill and the `task_dir` op's help (the op makes one for a session spawned before). A PreToolUse hook on Bash in every Claude Code session's `--settings` (`src/providers/git-tmp-guard-hook.ts`) refuses the session's own `git clone`/`git worktree add`/`git commit` in a temp dir, reading only the command it typed (a deploy's or a test's own scratch clone is untouched); `WALNUT_TMP_GIT_GUARD=0` turns it off. A PostToolUse hook on Write (`src/providers/tmp-write-note-hook.ts`; 2026-10-26: a Slack draft and a plan file in /tmp were swept the same day) never refuses: after a Write of a draft, plan, note or evidence file into a temp dir (prose formats such as `.md` always, any other name only when it or a directory carries a word like draft, plan, notes, evidence, report; never images, video or `.log`) it adds one line of context naming the task directory to move it to; `WALNUT_TMP_WRITE_NOTE=0` turns it off. Both share one temp-path test (`tmp-path-awk.ts`). **A clone keeps its source's commit identity** (`src/providers/clone-identity-hook.ts`, one Bash hook on PreToolUse and PostToolUse; 2026-10-28: agents' landing clones of a checkout with its own identity committed and rebased under the machine's global one, and their pushes carried it): a session's `git clone` of a LOCAL repository is noted before the command runs, read from the directory it starts in (PostToolUse's cwd is where the command ended), and once the clone is checked out (at that command's end, or before the session's next command when it failed or ran in the background), a clone with no identity of its own whose remote points at that source gets the source's `user.name`/`user.email` in its local config, and one line of context says so; URLs, a clone with its own identity, a directory that is not that source's clone and a clone still running are left alone. It reads the command with the same parser as the temp-dir guard (`git-command-awk.ts`, its JSON read linear in time); `WALNUT_CLONE_IDENTITY=0` turns it off. A task transfer carries the identity the source repository sets for itself, never the machine's, in its pack (`identity` in the meta), and the new session's setup steps set it on a fresh clone, or on a checkout of the target that commits as the machine does. Cleanup (`src/core/task-dir-sweep.ts`, primary only, every 6 h): the server picks directories whose task completed 7+ days ago (`WALNUT_TASK_DIR_KEEP_DAYS`) and that nobody used since, and the host removes each only when no repo in it has uncommitted or untracked files, a stash, or commits no remote has. A day after completion (`WALNUT_TASK_DIR_PRUNE_DAYS`, 0 = off; capability `task-dir-prune-v1`, `pruneTaskDirs`; 2026-10-31: task directories held 27 GB, mostly clean clones and node_modules of finished tasks) the host first prunes it, once per use: each repo in it that holds nothing unique and no ignored file but build output goes, unless a repo anywhere under the root borrows its objects (`clone --shared`), and so does build output git does not track (`node_modules`, `DerivedData`, `.build` anywhere; `dist` and test reports only when the repo ignores them); the directory's mtime is put back. Tests and ephemeral servers point `WALNUT_TASK_DIR_ROOT` into their own temp dirs. Scripts keep evidence via `scripts/lib/evidence-dir.{mjs,sh}`. Ratchet: `tests/core/work-place-rule.test.ts`.

## A session whose working folder is gone keeps working

- **A session whose working folder is gone keeps working** (`src/core/sessions/folder-gone.ts`; 2026-10-30, the user: "as long as Claude Code has the chat history ... don't recreate the original folder ... let it continue working"; a peer's message to a session in a reorganized notes folder was parked as "Working directory no longer exists" and Retry failed the same way). It never recreates the old folder: it moves the Claude Code transcript and its `<sid>/` sidecar into the project dir of the task's own directory (the CLI resumes a copy in its own folder's project dir first, and names that dir by the folder's real path), points the record (and `task.cwd` when it was the gone folder) there, and sends what waited, the first message carrying a one-time `outcome="folder-moved"` notice (or the next message, `pendingFolderMovedNotice`). With the history gone too it starts a new conversation for the task there, carrying the waiting messages and the task's summary, and the old session is detached only once that start spawned. ACP engines (Codex resumes a thread by id from any folder) only change folder.
